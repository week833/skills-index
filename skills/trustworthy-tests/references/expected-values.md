# 可信的斷言與預期值

本頁改寫自上游的 `writing-good-tests.md`（出處與授權見 [NOTICE.md](../NOTICE.md)）：範例改成 Python／pytest，刪去與使用者規則衝突的部分，並加上研究程式常見的陷阱。標示「實測」的事實，其版本與平台列在 NOTICE.md 的「已驗證」；沒有標示的是作法建議。

## 1. 先說出這個測試要抓的錯

寫測試本體之前，先用一句話回答：**程式被改成什麼樣子時，這個測試應該失敗？那個改動是錯誤，還是有意的決定？**

| 你的回答 | 怎麼辦 |
|---|---|
| 說得出一種錯誤：走錯分支、少了副作用、參數錯、邊界值、契約被破壞 | 照這句話寫測試，並把它寫進測試名稱或註解 |
| 說不出來 | 改測一個看得見的行為：輸出、副作用、丟出的例外 |
| 「原始碼的文字變了」 | 不比對文字；用受控的輸入執行它，斷言輸出、副作用或退出碼 |
| 只有有意的決定會讓它失敗：常數的值、訊息用字、私有結構 | 這是變更偵測器；改測依賴那個決定的行為 |

- 一個測試只測一個行為；名稱寫出行為，名稱裡需要「以及」就拆成兩個。
- 變更偵測器的例子：`assert HORIZON == 63` 只在有人改常數時失敗；該測的是「第 t 列的標籤等於第 t+63 列收盤價相對第 t 列的報酬」。
- 給人讀的文件不寫測試；文件與程式不一致時的處理依專案的 AGENTS.md。

## 2. 預期值要獨立推導

預期值若是受測程式（或它的輔助函式）自己算出來的，程式怎麼錯，測試都會通過。

```python
# 不可信：兩邊都是受測函式算的，永遠相等
expected = forward_return_correct(panel, 2)
np.testing.assert_allclose(forward_return_correct(panel, 2), expected)

# 可信：手算，不經過受測函式（第 0 列是 121/100-1 = 0.21；最後兩列沒有未來價格）
expected = [121 / 100 - 1, 110 / 110 - 1, 99 / 121 - 1, 108 / 110 - 1, np.nan, np.nan]
np.testing.assert_allclose(forward_return_correct(panel, 2)[:6], expected, rtol=1e-12, atol=0.0)
```

上面的名稱取自[範例檔](../examples/test_pit_patterns.py)，完整版本是其中的 `test_d_forward_return_matches_hand_values`。

作法依優先順序：

1. 字面值：把資料縮到可以手算，手算過程寫在註解裡。多組輸入用 `pytest.mark.parametrize`，每組配一個字面預期值。
2. 另一種獨立的方法：例如用迴圈逐列計算，對照向量化的實作。兩種方法不可共用輔助函式。
3. 性質檢查：預期值算不出來時，改檢查一定成立的性質，例如 [pit-test-patterns.md](pit-test-patterns.md) 的截斷不變性。性質檢查抓不到「沒有前視但算錯」，所以至少再配一兩個手算值。

由受測程式產生後存檔的快照不是獨立推導：它只能發現結果變了，不能證明結果是對的。要用快照時，先手算核對其中幾列，並在回覆中說明核對了哪幾列。

手算時容易弄錯的定義（實測）：

- 標準差：`pandas.Series.std()` 預設 `ddof=1`；`numpy.std()` 預設 `ddof=0`；scikit-learn `StandardScaler` 的 `scale_` 等於 `ddof=0` 的標準差。
- 視窗：`rolling(3)` 的前兩列是 NaN；`rolling("3D")` 這種時間視窗，只要視窗內有一列就會算出數字。
- 位移：`shift(1)` 讓第 t 列拿到第 t-1 列的值；`shift(-1)` 讓第 t 列拿到第 t+1 列的值。
- `pandas.merge_asof` 預設 `direction="backward"`、`allow_exact_matches=True`，鍵值相同的那一筆也算符合。

## 3. 數值比較與容差

浮點數不用 `==` 比較。三種工具的預設值（實測）：

| 工具 | 預設容差 | 注意 |
|---|---|---|
| `pytest.approx(預期值)` | 相對 1e-6、絕對 1e-12 | NaN 預設不相等，需要時加 `nan_ok=True`；可以包住 list 與 dict |
| `numpy.testing.assert_allclose(實際值, 預期值)` | `rtol=1e-07`、`atol=0` | 同位置的 NaN 視為相等；預期值是 0 時要自己給 `atol` |
| `pandas.testing.assert_frame_equal`、`assert_series_equal` | 相對約 1e-5、絕對約 1e-8 | 同時比對 dtype、索引與名稱；整數欄對浮點欄會失敗 |

- 容差要明寫。檢查「結果不該變」時用很嚴的容差，例如 `rtol=1e-12, atol=0.0`；與手算值比對時，容差不能比手算值的有效位數更嚴。
- `numpy.allclose` 與 `numpy.isclose` 預設把 NaN 當成不相等（要加 `equal_nan=True`），與 `assert_allclose` 相反（實測）。

## 4. 測自己的程式，不測框架，也不測 mock

- 不測 pandas、numpy、scikit-learn 本身的機制。只有當它的行為曾經出乎意料時，才寫一個範圍很窄的測試，並把假設寫進名稱，例如「`merge_asof` 預設會收同一天」。
- 建構子、取值函式、常數與單純轉手的函式不單獨測，除非它會驗證、正規化、補預設值、推導或產生副作用；否則改測第一個看得見、而且依賴它的結果。
- 不對 mock 斷言。那種斷言只證明 mock 在場，對受測程式什麼都沒說。
- 研究程式優先用小型合成 DataFrame 跑真的計算。只把慢的或對外的那一層換成替身，例如網路、中央資料、訊息傳送；先弄清楚被換掉的函式原本有哪些副作用，測試依賴的部分要保持真實。
- 替身的資料要照實際結構把欄位給齊，不是只給測試讀到的那幾欄。參數、呼叫次數或順序若屬於契約，就要斷言；成功、失敗、格式不符各用各的假資料。
- 只有測試用得到的清理或輔助函式，放在測試檔或測試工具裡，不加進既有程式。
- 替身的設定比測試邏輯還長，或說不出為什麼需要它時，改寫成使用真實元件的小型測試。

## 5. 隔離：測試不碰外面的世界

- 資料：手打，或用固定種子（`numpy.random.default_rng(固定整數)`）產生的小型合成資料；不讀專案的正式資料或中央資料。
- 檔案：只寫在 pytest 的 `tmp_path` 底下；路徑用 `pathlib`，讀寫都明寫 `encoding="utf-8"`。
- 設定：受測程式會讀環境變數或固定路徑時，用 `monkeypatch.setenv` 或 `monkeypatch.setattr` 把它指到 `tmp_path`。不確定它會讀哪裡，就先問使用者。
- 憑證：測試資料不放真實的 token、帳號或含 token 的 URL；不印出環境變數。
- 時間：不依賴「今天」；把基準日當成參數或固定值傳進去。
- 不連網、不傳訊息；不跑正式的訓練流程，不讀寫正式的模型檔。在測試內的合成小資料上，以固定的 `random_state` 擬合估計器可以。

```python
def test_reader_keeps_chinese_names(tmp_path):
    path = tmp_path / "names.csv"
    path.write_text("stock_id,name\n0001,測試股\n", encoding="utf-8")
    frame = pd.read_csv(path, dtype={"stock_id": "string"}, encoding="utf-8")
    assert frame.loc[0, "stock_id"] == "0001"
    assert frame.loc[0, "name"] == "測試股"
```

## 6. 確認測試會失敗

沒看過它失敗的測試，不知道它抓不抓得到錯。

先在腦中把受測程式改壞。每一種實際可能發生的改法，至少要有一個測試會失敗：常數或參數錯、走錯分支、少了狀態改變或副作用、回傳空值或預設值、少了對零、空、缺值或格式不符輸入的檢查。研究程式常見的改法：位移方向相反、視窗長度差一、`allow_exact_matches` 的真假、漏了 `groupby`、`ddof`、訓練窗的邊界差一列。沒有任何改法能讓測試失敗，表示那個行為沒有被保護，或者測試恆真。

實際作法分四種情況。

### 6.1 新行為：紅燈在前

先跑新測試、看它失敗，再寫程式。紅燈只認一種失敗：斷言失敗，而且實際值與預期值都如你所料。

- 要新增的名稱還不存在時，先在受測模組寫一個回傳明顯錯誤值的空殼（例如固定回傳 `-1.0`），看到斷言失敗再實作。只看到「名稱不存在」的錯誤，證明不了斷言抓得到錯。
- 拼字、匯入路徑、fixture 或建立資料時出的錯都不算；先修好測試，再跑一次，直到失敗原因正確。

實測（pytest 9.2.0）：在測試函式裡呼叫還不存在的函式，顯示 `1 failed`、退出碼 1，錯誤是 `AttributeError`；在測試檔頂端匯入不存在的名稱或模組，顯示 `1 error`、退出碼 2；換成回傳 `-1.0` 的空殼後，顯示 `1 failed`、退出碼 1，訊息是 `assert -1.0 == 0.21`。三種之中只有最後一種算紅燈。

新測試第一次跑就通過，表示這個行為早就存在，或測試沒有測到東西；改走 6.2 或 6.3，不可以直接當成完成。

### 6.2 既有行為：經使用者同意的突變檢查

程式已經存在時（包含「程式先寫好、測試後補」），測試一寫就會通過。既有程式原樣保留，不刪除、不重寫；用下面的步驟取得紅燈。**暫時修改既有程式需要使用者同意。** 受測程式不在 git 儲存庫內，或機器上沒有 git 時，無法核對變更範圍，不做這一節：改用 6.3，或在回覆寫「未做突變檢查」。

1. 徵求同意。說明：要改哪個檔案的哪一行、改成什麼、會跑哪一個測試、改完立刻還原。同時說明：修改期間任何載入該檔案的行程（例如執行中的服務或排程）會執行到改過的內容；有這種可能時，先建議改用 6.3 的行程內突變。使用者不同意就不改程式檔：改用 6.3 的作法，或在回覆寫「未做突變檢查」。
2. 記下基準（路徑為範例）：
   - `git status --porcelain --ignored --untracked-files=all -- src tests`
   - `git diff --stat`
   - `git hash-object --no-filters src/labels.py`
3. 用編輯工具只改一處，而且是最小的改動，例如把 `shift(-h)` 改成 `shift(h)`。不整檔覆寫，不改換行符號或編碼。
4. 跑目標測試，用第 7 節的指令：同一行先設 `$env:PYTHONDONTWRITEBYTECODE='1'`，再帶 `-B` 執行（理由見下方）。修改與還原之間只執行這一個指令，不做別的事。預期它失敗，而且失敗訊息對得上這個改動；輸出記在回覆裡，不另存成檔案。測試沒有失敗時有三種可能：這個行為沒有被保護；這個改動在測到的輸入上不會改變結果；測試載入的不是你改的那個檔案（例如 conftest.py 把固定的絕對路徑加進 `sys.path`）。不論哪一種，都先完成步驟 5 到 6 的還原，再判斷原因；載入的是哪個檔案，靠閱讀 conftest.py 與測試檔裡改動 `sys.path` 的地方判斷，不另外執行會匯入程式模組的指令，因為匯入就會執行模組層級的程式。要加強測試或換一種改法重做，都要重新徵求同意。
5. 不論測試結果如何（失敗、通過、逾時或出錯），立刻把那一處改回原來的文字。不使用 `git checkout --`、`git restore`、`git reset`、`git stash` 來還原。
6. 驗證還原：重跑步驟 2 的三個指令。雜湊必須與基準相同；`git status` 的清單與基準相比，只能多出預期的測試檔；`git diff --stat` 與基準相比，只能多出預期修改的既有測試檔。然後再跑目標測試，確認通過。
7. 雜湊不同或清單多出預期以外的項目時就停手，不再修改、刪除或還原任何東西；把前後的雜湊、清單與 `git diff -- src/labels.py` 的輸出交給使用者決定。貼出前先確認沒有 token 或含 token 的 URL，有就遮蔽。
8. 回覆列出：改動的內容、失敗輸出、還原前後的雜湊、通過輸出。

這樣驗證的理由（實測，git 2.43.0）：

- `git diff --stat` 不會列出未追蹤的新檔；`git status --porcelain` 會，開頭是 `??`。新資料夾預設只顯示資料夾名稱，加上 `--untracked-files=all` 才逐檔列出。
- `git status` 預設不列出 .gitignore 忽略的路徑，例如 `__pycache__` 或輸出資料夾裡的新檔；加上 `--ignored` 才會以 `!!` 列出，再加 `--untracked-files=all` 才逐檔列出。用 `-- 路徑` 限定在受測與測試資料夾，不會列出整個虛擬環境。
- 檔案原本就有使用者未提交的變更時，再改一次，`git status` 前後都是 ` M`；只有 `git diff --stat` 的行數與雜湊看得出它又被改過。
- `git hash-object --no-filters` 直接對檔案的位元組算雜湊，檔案有沒有被追蹤都能用，在 git 儲存庫外也能用；但儲存庫外的 `git status` 以退出碼 128 失敗。該檔案原本就有使用者未提交的變更時，`git diff` 前後都有輸出，仍可用雜湊確認「改回去之後與改之前相同」。
- 在 `core.autocrlf=true` 的儲存庫裡，只把換行符號從 LF 改成 CRLF 時，`git diff` 沒有輸出，但 `--no-filters` 的雜湊不同。使用者機器上的這項設定未能確認。
- `git checkout -- 檔案`、`git restore 檔案`、`git reset --hard` 會丟掉該檔案裡未提交的變更，`git stash` 會把它們從工作目錄移走；所以不拿來還原。
- 突變期間不可以留下快取（實測，Python 3.12.3）：改壞的版本若被寫成 `__pycache__` 快取，而還原後的檔案大小與修改時間（到秒）又剛好與改壞時相同，Python 會繼續執行改壞的那份快取。`-B` 只讓 pytest 這個行程不寫快取；測試另開 Python 子行程（例如用 `sys.executable` 執行）時，子行程照樣寫出快取。子行程沿用的環境變數 `PYTHONDONTWRITEBYTECODE=1` 讓兩邊都不寫。這種快取在 .gitignore 忽略的 `__pycache__` 裡，雜湊與一般的 `git status` 都看不出來。

### 6.3 不改動程式檔的作法

這兩種作法都比 6.2 弱，不算突變檢查：回覆仍寫「未做突變檢查」，並在括號內註明做了哪一種。

- 行程內突變：要改的是模組層級的常數或函式時，在測試裡用 `monkeypatch.setattr` 暫時替換，再斷言檢查會失敗。磁碟上的程式檔沒有被改動，該測試結束後替換會復原（實測）。這個方法改不到寫在函式內部的字面值；實測也改不到在匯入時就綁定的預設參數（`def f(h=HORIZON)`），以及其他模組用 `from 模組 import 名稱` 取走的複本。替換後檢查沒有失敗時，先確認受測函式讀的是不是被替換的那個名稱。`pytest.raises` 要用 `match=` 指定預期的失敗訊息，並在同一個測試裡先確認未替換時檢查會通過；少了這兩步，檢查本身因為別的原因失敗時，這個測試也會通過（實測）。這個測試要不要留在測試檔，由使用者決定。回覆寫成「未做突變檢查（只做了行程內突變：替換 `labels.HORIZON`）」這類寫法。

```python
def test_label_check_detects_wrong_horizon(monkeypatch):
    check_forward_return()  # 未替換時必須通過
    monkeypatch.setattr(labels, "HORIZON", 3)
    with pytest.raises(AssertionError, match="wrong label at row 0"):
        check_forward_return()
```

- 反例對照：把檢查寫成「接受實作當參數」的函式，另外給它一個故意做錯的實作，斷言檢查會失敗；範例檔就是這樣寫的。這只證明檢查本身會失敗，不證明專案裡的真實程式有被測到，所以回覆寫「未做突變檢查（只做了反例對照）」。

### 6.4 既有程式上的新測試一跑就失敗

這不是待修的紅燈，而可能是發現了問題。

1. 先重新推導預期值：換一種方法再算一次；規則本身不明確時（例如「t」的時點定義），問使用者。預期值錯了就改測試，再跑一次。
2. 預期值沒錯，就是受測程式的行為與預期不同。不改程式，也不為了通過而改測試或放寬斷言；回報指令、失敗輸出、手算過程與判斷。
3. 測試怎麼處理由使用者決定：保留（專案的測試入口會因此失敗）、先不加，或標成預期失敗。標成預期失敗時用 `pytest.mark.xfail(strict=True, reason=...)`：測試照舊失敗時統計行是 `1 xfailed`、退出碼 0；程式被修好、測試意外通過時是 `1 failed`、退出碼 1，訊息含 `XPASS(strict)`（實測，pytest 9.2.0）。
4. 使用者要求修正時，這個失敗就是紅燈；修正後再跑一次，看到通過。

## 7. 執行與判讀 pytest

指令（PowerShell 單行；路徑與名稱為範例，`python` 換成專案自己的直譯器）：

`$env:PYTHONDONTWRITEBYTECODE='1'; python -B -m pytest -q -p no:cacheprovider tests/test_labels.py::test_label_alignment`

- `-B` 讓 pytest 這個行程不寫 `__pycache__`；`PYTHONDONTWRITEBYTECODE=1` 連測試另開的 Python 子行程也不寫；`-p no:cacheprovider` 不留 `.pytest_cache`（實測）。`$env:` 是 PowerShell 設定環境變數的寫法，其他 shell 改用該 shell 的寫法；這一行沒有在 PowerShell 實際執行過（見 NOTICE.md）。
- pytest 會自動載入測試資料夾與各上層資料夾的 `conftest.py`，以及 `pytest.ini` 這類設定檔裡的 `addopts`（實測：上層資料夾的 conftest.py 被執行；`addopts` 裡的 `-k` 讓一個會失敗的測試被取消選取，結果是 `1 passed, 1 deselected`、退出碼 0）。跑既有測試之前先讀這些檔案。
- 例（使用者 stock 專案 a74eb97 版的 `programs\RUN_ALL_TESTS.cmd`，只讀過、沒有執行）：檔案開頭設定 `PYTHONDONTWRITEBYTECODE=1`；直接呼叫 pytest 的 7 行裡，6 行用根目錄的 `.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider` 測本專案，最後 1 行用另一個專案的直譯器跑另一個專案的測試，不照用。這個檔案還會執行 PowerShell 檢查與 Pester 測試，結尾除非設了 `STOCK_TOOLKIT_NO_PAUSE=1`，否則會停下來等按鍵；所以只拿來看直譯器與參數，不直接執行，除非使用者要求。

實測（pytest 9.2.0）：

| 情況 | 統計行 | 退出碼 |
|---|---|---|
| 全部通過 | `3 passed` 這類 | 0 |
| 通過，但有警告 | `1 passed, 1 warning` 這類 | 0 |
| 只有被跳過的測試 | `1 skipped` | 0 |
| 只有標成預期失敗的測試 | `1 xfailed` | 0 |
| `-k` 沒有選到任何測試 | `5 deselected` 這類 | 5 |
| 測試名稱打錯 | `no tests ran`，並有 `ERROR: not found` | 4 |
| 收集階段出錯 | `1 error` | 2 |

退出碼 0 不等於通過。回報時貼出統計行，並核對 `passed` 的數量等於預期要跑的測試數；有 `skipped`、`xfailed`、`deselected` 就要說明原因；有 `warning` 就列出警告並說明。例如把小數寫進整數欄時，pandas 2.3.3 發出 `FutureWarning`，測試照樣通過、退出碼 0（實測）。

## 8. 警訊

出現下列情況就回頭檢查測試：

- 準備資料與斷言用的是同一個物件，必然相等。
- 測試只可能因為程式當掉而失敗。
- 每次有意的修改它都失敗，真的出錯時卻不會。
- 預期值藏在迴圈、產生器或輔助函式後面。
- 測試在搜尋原始碼的文字，或斷言某個被移除的名稱仍然不存在。
- 就算只剩框架，這個測試依然成立。
- 為了涵蓋率而寫，沒有檢查任何結果或副作用。
- 斷言的對象是 mock，或拿掉 mock 測試就失敗。
- 某個函式只有測試檔在呼叫。
- 替身的設定超過測試的一半，或只是「保險起見」才用替身。
- 新測試第一次跑就通過，卻沒有用 6.2 或 6.3 的作法確認過它會失敗。
